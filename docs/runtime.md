# 邮件入口与事件工作流实现

记录日期：2026-10-21。Gmail 邮件读取、过滤与风险识别已经实现；真实入口是 poll / watch，run 保留已识别事件列表的学习入口。

## 邮件读取与风险识别

`gmail.py` 使用 Google 官方 OAuth 库取得桌面应用只读凭证，再调用 Gmail REST API。首次运行 auth 打开系统浏览器，用户完成登录及权限确认；凭证存入忽略的 `data/gmail-token.json`，支持刷新。OAuth 凭据与账户授权是两回事；auth 还实际调用 profile 验证 API 权限。个人测试应用需要在 Google Cloud 的 Audience / 测试用户中加入登录邮箱；未加入时会收到403 access_denied。

每次 poll 或 watch 轮询以开始时刻为终点，读取前两小时的邮件。检索使用秒级 Unix 时间戳，并用 internalDate 毫秒值做本地边界检查；不依赖邮件自报 Date 或含糊的时区日期。默认排除垃圾邮件、回收站、草稿及仅在已发送中的邮件；已归档邮件和收件箱中的自发邮件仍可读取。不会标记已读、移动、删除或回复邮件，不下载附件。优先提取纯文本，否则转为 HTML 文本并去掉脚本和样式。

读取后先持久化到 `mail_messages` 待识别队列。Gmail 账号哈希和 message_id 组成邮件身份，避免跨账号误去重；同账号中的相同发件人/主题/完整提取正文也按重复内容跳过。正文截断或只有摘要时不跨 message_id 合并。识别成功后清除队列原文；有风险时原始证据保留在事件里。无风险邮件也记录处理结果，重叠窗口不会重复调用模型。识别失败不记为“无风险”，本地缓存保留，即使之后超过两小时仍可重试。待识别队列优先未尝试项、再按上次尝试时间重试，避免一批持续失败的邮件挡住后续邮件。

`inbox.py` 构建 `read_recent_mail → identify_service_risks` 图。千问返回零到多个风险，包含服务、账号、状态、可确定的时间和逐字原文证据。程序验证证据来自邮件，再构造真实 IncidentSeed；source_ref 和 simulated=False 由代码确定，模型不能自行伪造来源。每个服务/账号一条；一封邮件里有三种账号风险则登记三个独立事件。整封邮件的事件登记和处理标记使用同一 SQLite 事务，中途失败不会静默丢掉后面的事件。

邮件入口先登记事件，再调用原有 tick 图处理未完成首次事件和到期任务，避免同一事件被两个执行入口同时处理。Gmail 不可用或识别失败也继续处理此前登记的事件与独立提醒。

默认每轮最多取10封未处理邮件，每封正文最多12000字符，分页最多100页；达到限制输出 has_more，需按邮箱量调整 `gmail_max_messages`、轮询间隔及 `llm_max_calls`。模型预算用尽的事件保持未完成，下一轮重试。正文之外的附件/截断部分可能含风险，当前不保证识别这部分；也不保证模型零漏报。停机超过两小时不补读更早邮件，这是用户指定的窗口行为。

## 输入、身份与时间

一个输入元素对应一个风险事件，包含服务、账号标识、原始通知标识、通知文字、停用状态和可选生效时间。单封通知涉及三个账号时，构造三个元素；共同 source_ref 也可以，因为 account_ref 参与事件身份。

`event_id` 从 `source_ref + service + account_ref` 生成。同名服务不同账号不合并；同账号不同通知不合并；同条通知同账号的重复输入不重置时钟。事件创建时间由首次登记固定，24小时复查不依赖待办文件。

示例中“两个月后”仅是模拟通知的设定，不代表 giffgaff 官方停用周期。三个账号均为虚构，所需行动只输出建议，不执行申诉、购买或账号操作。

## 模型与资料边界

事件学习入口的模型可选择 `qwen` 或 `demo`，资料可选择 `youtube` 或 `fixture`；真实邮件入口要求 qwen 和真实时钟。真实千问走用户配置的兼容地址，关闭思考、限制输出和每轮调用数。Gmail 凭据只用于邮箱访问，不进入模型提示词；邮件正文按用户指定流程交给千问分析。

搜索词使用“服务/对象＋日常问题词”，第二路追加“申诉”，第三路追加“应对处理方式”；程序固定拼接，不调用模型扩写成正式长句或自动改成英文。要求包含服务名，拒绝账号标识或邮箱符号，不把模拟通知当成研究主题。字幕/邮件/网页仅作不可信资料，不授予工具权限。收件人固定在配置中；模型不能生成新的通知目标。提炼节点收到事件、研究目标与资料，仅将实际相关且被提炼引用的 source_id 送入方案；不相关、无字幕及提炼失败的候选仅留在本地诊断JSON，不展示为用户可用来源。

`risk_policy.py` 构建注入各研究/生成节点的 `business_context`，含七天紧急窗口、评估时钟、距截止小时数、当前事件状态和模拟情境处理要求。已停用/取消、截止已过及七天内需处理的停用/暂停/核验统一判紧急，模型不能降级；未知时间不自动虚构期限。七天整按紧急，超过七天仍交由模型结合通知判断。七天是用户的提醒阈值，不能当成服务商宽限期或搜索条件；也不把其他风险类别添加到本次事件。模拟标记在最终交付说明一次，不改变给定情境中的风险级别和研究主题。

`delivery.render` 输出简版用户报告：情况说明、最多三项去重动作、最多两个实际相关来源；时间以北京时间显示，不输出内部ID、三路摘要、节点状态、判断依据及整段限制。若完全没有可引用资料，保留一句人工核实提示。完整方案字段、查询、材料、提炼和失败状态仍保存在原JSON报告。既有已完成报告不会被自动重跑或重发；新版输出从下一轮新处理开始生效。

每个方向获取前5个视频并逐一尝试字幕。当前配置每个视频独立最多50000字符；已经取得的字幕全部进入该路提炼，不再让第一份字幕耗尽整路预算后挤掉后面的资料。超过单视频上限仍明确标记截断；无字幕、IP阻断和请求失败分别记录，不能假装已读正文。字幕时间点、URL、标题和可取得的发布日期保留在报告中。工具子进程超时或取消时会终止，不在后台继续占用。

转写文稿先枚举可用语言，按配置优先级匹配，并兼容 zh / zh-Hans / zh-Hant；没有首选语言时使用实际存在的其他轨道。取文稿失败时用 yt-dlp 仅读取作者简介，过滤独立推广/联系链接行；Material.content_kind 区分 transcript、description 和旧记录的 unknown，语言与失败原因保留并送入提炼模型。简介没有伪造字幕时间点，也不代表已读取完整视频。单视频仍共用 tool_timeout_seconds 总预算，转写最多占12秒或一半预算，剩余时间留给简介兜底。

`fixture` 是官方页面的人工整理演示摘要，不是视频字幕。实时来源失败时不会自动切换到它。真实模型或研究失败保留事件和失败报告，另一个事件仍可独立完成。

## 持久化与重新执行

`data/monitor.sqlite3` 保存事件台账、独立提醒、通知回执与运行记录；`data/reports/` 保存每个事件本轮的完整报告；`data/outbox/` 保存待交付通知正文。

普通事件初次写入待办后完成首次交付。待办检查不读取或改写计数文件；3小时到期且文件仍在则发送升级通知，成功后只提醒一次。文件不存在取消该提醒；无法读取保留异常，不当成用户已处理。

所有事件在首次登记24小时后重新走研究流程，无论普通、紧急或待办被删除。完成方案后均进入通知节点，发送成功才标记本次复查完成。暂存和发送失败不标记成功。重试交付复用本轮报告，不重新研究；24小时复查本身则一定是新研究，不复用初次研究。合成失败会保留已取得的三路结果，重试该节点不用再次搜索。

提醒记录保存所需事件与方案快照，不通过外键级联删除；即使复查侧记录被移除，待办提醒也不会被自动取消。代码不提供永久删除事件或级联清理命令。

同一数据目录有进程锁，避免两轮并发执行。成功回执持久化去重，但外部通知已接受、进程却未能写回回执的崩溃窗口仍可能造成重试重复；不宣称网络发送严格恰好一次。

## 当前取舍与未决定的行为

- 24小时只实现每个事件至少一次必须复查；是否此后每日循环未定，不擅自循环。
- 不在更新后自动删事件、待办或提醒，不自动将问题标记已解决。
- 初始紧急事件通知，不额外创建待办或新增3小时重复告警。
- 已提供前台 watch 命令，每轮读最近两小时邮件并检查提醒；未创建或启动系统计划任务或后台服务。
- 默认只写本地发件箱；使用 `--notify` 才经 Apprise 发送到配置的 Telegram，可额外加入邮箱通知配置。

## 验证方法

`python -m pytest -q` 使用临时目录、固定时钟及模拟工具，验证邮件时间边界、分页和去重、MIME/HTML、多个风险独立处理、事务失败回滚、识别失败跨窗口重试、Gmail 失败不取消提醒，以及原有的两条时间机制、等待屏障、超时回收和发送重试。测试不访问真实邮箱，不发送 Telegram 消息，也不按真实时间等待3小时或24小时。

## 本次实际验证

- 离线演示：三个模拟号码分别完成事件图并写出三个独立待办。
- 真实千问 + 固定演示资料：单个事件完成6次模型调用并生成待办，使用独立的 `data-qwen-check` 目录。
- 真实千问 + YouTube：三个事件均完成首次处理，分别写入桌面 `tryy`。A取得2份字幕，B取得2份，C未取得可用字幕；C仍输出证据不足和人工核实方案，没有伪造来源。完整资料和时间点保存在本地 `data/reports/`。
- 初次真实校验发现模型会引用未取得字幕的视频，现已由程序维护最终来源列表，并有对应回归测试。失败后的方案合成可复用已取得的研究结果。
- Gmail：用户完成浏览器登录及只读授权，profile 验证成功。北京时间2026-10-21 12:48实际读取最近两小时的2封邮件，真实千问判为无风险；约12:50重复读取时2封均去重，模型调用0次。真实邮件未触发风险事件，因此这次真实邮箱运行没有进入 YouTube 研究。
